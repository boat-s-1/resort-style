# 女の子マイページ業務アプリ化 — 最終目標と実装計画

対象: `boat-s-1/resort-style`。基点: PR #63 マージコミット `6a9a76a36021e9e69f8023a964087127973d0c2a`。MarroN と Resort-style の既存予約・会計・出勤・ルーム管理・マイページを再利用する。別システムを作らない。

## 完成条件

女の子はスマートフォンから本人の予約、当日の確定給料・接客件数、次の予約と終了予定、7営業日分のルーム空き、出勤申請と予定・実績、仕事開始・終了、延長申請、スタッフとの連絡、お知らせ、SNS・媒体アカウントを扱える。スタッフは店舗権限に従い、管理画面と希望する端末で状況と通知を受け取る。iPhone/Android の実機 Push、PC/スマホ、重複・権限・会計分離を検証して初めて日常運用可能と判定する。

## 現状確認（2026-11-27）

- `/mypage` は `resort_therapist_login` と期限付きセッショントークン、`resort_mypage_action` を使用。本人予約、給料、出勤申請、発行済みアカウントを取得する。予約の顧客情報は既存の本人向け投影に含まれない。
- 管理画面は Supabase Auth と `resort_admins` で認証。`resort_schedule_rooms` は管理者 RLS、出勤申請と媒体の秘密は `resort_private` の RPC を通す。既存の管理者判定は全店舗共通で、店舗別スタッフ権限は未実装。
- `resort_bookings` は `therapist_id`、`booking_date`、`start_time`、`duration_minutes`、`room_number`、`status`、会計金額を保存。`resort_schedules` と `resort_schedule_rooms` は出勤とルーム割当を保存。管理者の `RoomTimeline` は10:00〜翌05:00を表示する。
- 仕事開始・終了イベント、訂正履歴、延長申請、スタッフ連絡、通知履歴・既読、Push購読、清掃・利用停止は現行スキーマにない。既存の予約 `status=completed` は会計完了なので、仕事終了に流用しない。
- 管理者の予約・出勤保存は現在複数操作で行われる。承認時のルーム衝突再確認は DB トランザクション内にない。これを導入するまで「空きあり」は確保を保証しない。
- 本番のRLSを読み取り専用で照合した。`resort_bookings` と `resort_schedule_rooms` は管理者のみ。一方 `resort_schedules` には匿名SELECTの公開サイト用ポリシーがあり、Resort-styleの出勤を読める。マイページのルーム表示はこの公開テーブルを直接取得せず、他人の行やIDを含まない専用RPCからのみ取得する。公開サイト用RLSの変更は別途影響評価が必要。

## 不変条件とデータ境界

1. 本人向け RPC は毎回トークンのハッシュ・期限・アカウント有効性を確認し、予約の `therapist_id` をサーバー側で固定する。他人の氏名、予約、顧客、売上、給料、媒体資格情報を **SQL結果とAPIレスポンスに含めない**。ルーム空きはサーバー側で時間帯ごとに `空きあり/利用予定あり/自分の利用予定/利用不可` に変換し、他人のID・件数・詳細も返さない。
2. 仕事開始・終了は本人予約を行ロックしてサーバー時刻 `now()` で一度だけ記録。二重押しは同じ結果を返すか安全に拒否する。終了は会計・給与・予約ステータスを変更しない。訂正は管理者のみ、旧値・新値・理由・操作者・時刻を追記し、元の履歴を消さない。
3. 通知は `event_id` と宛先の一意制約で重複防止。管理画面は権限付き通知一覧を購読または短周期で更新し、未読と音ON/OFFを端末ごとに保持する。音はブラウザのユーザー操作後に有効化。ロック画面には「新しい業務連絡があります」等のみ表示する。
4. Push は VAPID秘密鍵をサーバーのみで管理し、購読は本人/スタッフの認証と店舗権限を検証する。購読解除、失敗記録、失効端末の無効化、再送の冪等性を備える。通知許可拒否でも画面内通知を使える。実際の送信は別承認まで行わない。
5. 出勤希望は既存の承認フローを使う。申請時と承認時に重複を調べ、承認時の同一ルーム・時間帯の衝突判定は単一DBトランザクションで行う。既存の管理者直接登録にも同じ制約が必要。

### 予定するRPC契約と監査

- `resort_work_action(action, token, booking_id)` は `mine/start/finish` のみ。本人トークンを再検証し、対象予約の行ロックを取得する。`start` は本人の有効予約にサーバー時刻を一度だけ記録し、`finish` は開始済みの予約だけを終了する。同じ操作の再送は元の結果を返す。`status=completed` や会計額は更新しない。
- `resort_room_availability(token, business_date)` は今日から6日後までの1営業日、在籍店舗のみ。返す列は店舗表示名・店舗ID・ブランド・ルーム番号・営業日・30分枠の状態だけ。状態は `available/busy/mine/blocked`。他人の行をブラウザへ転送してから隠す方式は禁止。予定外の状態、失効トークン、7日外の日付は拒否する。
- `resort_admin_work_events(store_id, cursor)` は管理者の許可店舗だけを返し、通知受信時刻と既読状態を別に管理する。スタッフ訂正は理由必須で旧値・新値・操作者・サーバー時刻を追記する。通知音設定は端末ローカルで、通知先権限はサーバーで判定する。
- `db/proposals/therapist-work-app.sql` は必要な非公開テーブルの**未完成の設計草案**。適用可能なMigrationではない。匿名ブラウザに直接SELECT/UPDATE権限を付与しない。購読端末情報、権限、競合防止、通知送信まで設計・隔離DB検証してから適用を申請する。

## 段階2のMigration候補と書き込み経路（追加）

適用順序は `db/proposals/therapist-work-preflight.sql`（読み取り専用）→ `therapist-work-app.sql`（非公開テーブル、本人・空き・訂正RPC）→ `therapist-room-guard.sql`（予約・出勤・割当・清掃停止の共通ロックとトリガ）→ `therapist-staff-notices.sql`（明示的店舗権限による通知受信者作成と履歴RPC）。各段階はトランザクション。隔離DBで検証し、既存重複件数が0または運用上の扱いが確定するまで本番適用不可。既存管理者には店舗別通知権限を自動付与しない。監査・通知記録が存在する場合、`therapist-work-rollback.sql` は削除を拒否する。

| 経路 | 現在の書き込み | 候補の共通ガード |
| --- | --- | --- |
| 管理者の予約登録・編集 | `Operations` が `resort_bookings` を直接 INSERT/UPDATE | 予約トリガ、同じ店舗・ルーム・営業日のアドバイザリロック |
| 予約の延長 | 同じ予約の施術時間・延長料金を更新 | 時間変更を予約トリガで再確認。会計計算は既存処理のまま |
| 管理者の出勤登録・編集 | `admin/page` が出勤とルーム割当を**別のHTTP操作**で保存 | 出勤と割当の各トリガ。片方だけ成功する現在のUIを単一RPCに変更する必要がある |
| 女の子の出勤申請承認 | `resort_mypage_action` が出勤をINSERT、ルームは未指定 | 承認後のルーム割当時にガード。承認時の同時割当を含む単一RPCは未実装 |
| 清掃・利用停止 | 現在は登録機能なし | `room_blocks` のトリガで予約・割当と競合確認。管理者登録RPCと権限が未実装 |

半開区間 `[開始, 終了)` を採用し、10:00〜翌05:00の営業日ごとにロックする。既存の出勤割当と本人予約の重なりは同じ人の利用として許し、異なる女の子の重複と清掃・停止との重なりを拒否する。予約同士は同じ女の子でも重複を拒否する。異なる複数ルームを一つの操作で変更する場合のロック順とデッドロック再試行は隔離DBで確認する。
